# Contributing to EdgeCenter

Thanks for taking the time to contribute. These rules apply to every repository in
this organization unless a repository ships its own `CONTRIBUTING.md`.

## Before you write code

- **Bugs.** Open an issue in the repository where the bug lives, using the bug
  report template. Include the version, the exact configuration or code that
  reproduces it, and what you expected instead.
- **Features.** Open an issue first and describe the use case. This saves you from
  building something that conflicts with work already in flight.
- **Security.** Do not open a public issue. Follow [SECURITY.md](SECURITY.md).

If you are unsure which repository a problem belongs to, file it against
[terraform-provider-edgecenter](https://github.com/Edge-Center/terraform-provider-edgecenter)
and it will be moved.

## Pull requests

1. Fork the repository and branch off the default branch. Check which one it is:
   `master` in `terraform-provider-edgecenter`, `edgecentercloud-go`,
   `edgecenterprotection-go`, `external-dns-ec-webhook`,
   `cert-manager-webhook-edgecenter` and `cdn-stats-datasource-plugin`, `main`
   everywhere else.
2. Keep the diff minimal. A bug fix changes what is broken and nothing else -
   reformatting neighbouring code makes the change harder to review.
3. Add tests for the behaviour you change.
4. Run the repository checks locally before pushing.
5. Open the pull request, fill in the template, and link the issue it closes.

Every repository is protected: changes land only through a pull request, and a
code owner has to approve it.

### Signed commits are mandatory

Repositories reject unsigned commits at merge time, so an unsigned branch cannot
be merged no matter how good the change is. Set up commit signing before you
start:

```sh
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
```

Then add the same public key to your GitHub account as a **signing key** (a key
added only as an authentication key does not count). Verify with
`git log --show-signature -1` and by the `Verified` badge on GitHub.

### Commit messages

Conventional commits with the issue key in the scope:

```
feat(TF-237): [reseller] move reseller resources into services package
fix(DNS-686): keep the trailing dot out of the CNAME diff
```

Use `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `ci`. The subject line
says what the change does, in the imperative, under about 72 characters. Put the
reasoning in the body - that is where reviewers look for it six months later.

## Go repositories

The Go modules share one toolchain and one set of targets. From the repository
root:

```sh
make build        # go build ./...
make test         # go test -race ./...
make lint         # golangci-lint run ./...
make fmt          # gofmt plus goimports
```

The Terraform provider names two of these differently: `make linters` runs
golangci-lint, and there is no blanket `make test` because its suites are split by
build tag. Run `go test ./...` there for unit tests.

CI builds, tests and lints on the Go version pinned in each repository's workflow:
**1.26** for the provider, `edgecentercdn-go`, `edgecenteredgemon-go` and
`edgecenterprotection-go`, **1.22** for `edgecentercloud-go`. Do not raise the `go`
directive in `go.mod` without raising the workflow in the same pull request.

Coverage is gated: `make cover-check` (or `make check-coverage`) must pass, and new
code should not push a package below the existing bar.

Style:

- Run `make fmt` before committing. CI fails on unformatted code.
- Names carry the meaning. Write comments only where the *why* is genuinely not
  obvious from the code - not to restate what the next line does.
- Errors are wrapped with context (`fmt.Errorf("create zone %q: %w", name, err)`),
  never swallowed.
- Follow the file next to yours. New patterns in an old package cost more than
  they are worth.

### SDK modules

Every SDK is a standalone module and the Terraform provider pins a tagged release
of it. A change is not visible to Terraform users until the SDK is tagged and the
provider bumps the version, so SDK pull requests should note whether a release is
needed.

### Terraform provider

Acceptance tests create real cloud resources and cost real money. They are behind
build tags and are not part of the pull request check - do not run them casually.
Unit tests and `make lint` are what CI enforces.

Regenerate documentation with `make docs` whenever you touch a resource schema.
The `docs/` tree is generated by `tfplugindocs`; edit the schema descriptions and
the `examples/` files, not the generated markdown.
